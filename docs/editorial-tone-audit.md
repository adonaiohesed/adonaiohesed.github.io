# 한국어 문체 통일 분석

## 확정 기준과 작업 상태

사용자가 정한 최종 기준은 **모든 글의 한국어 서술문을 ‘한다’체로 통일**하는 것이다.
기술 글, 안내 글, 개인 기록에 같은 기준을 적용한다. 개인 경험과 가치관은 그대로 보존한다.
이 문서는 교정 전의 분석 결과와 적용 절차를 정리한 기록이다.
실제 적용 결과는 [교정 결과](editorial-tone-results.md)에 기록했다.

분석 기준 커밋: `750ec588ad0be95cf9b85599b5e471bfa32bb898`.
현재 작업 트리의 수정 중인 글과 미추적 새 글도 읽기 전용 분석에 포함했다.
삭제 상태인 글은 현재 파일이 없으므로 240편 목록에 포함하지 않았다.

240편 전체를 Kramdown의 Markdown 구조로 읽어 문단·목록·제목·표·블록 인용을 구분했다.
코드와 인라인 코드를 제외한 문단·목록에서 한국어 종결어미 후보를 집계했다.
원문과 의미를 고려한 정독은 대표 글들과 독립 편집 검토의 12편 표본을 중심으로 수행했다.
240편 전체에 대해 문장별 의미 검토를 완료했다는 뜻은 아니다.

[글별 목록](editorial-tone-inventory.csv)에 파일, 카테고리, 문체 후보, 검토 플래그,
작업 트리 상태, 분석 당시 SHA-256을 기록했다. 이 값은 교정 우선순위를 잡는 보조 자료다.
자동 분류에는 의문문, 문장 안의 대화·프롬프트 예시, 짧은 메모에 따른 오탐이 있을 수 있다.
집계만으로 글의 완성도나 수정 필요성을 확정하지 않는다.

나중에 수정되었을 수 있고, 이 저장소에는 게시일 재분배 스크립트도 있다.

## 확인한 주요 차이

1. **한 글 안의 어미 혼용**
   - `_posts/2020-06-24-elasticsearch_concept.md:14`는 ‘도움이 됩니다’,
     같은 글 `:34`는 ‘클러스터로 동작한다’로 끝난다.
   - `_posts/2019-01-01-system_design_basic.md:14`는 같은 목록 항목 안에
     ‘해야한다’와 ‘설정해야 합니다’가 함께 있다.

2. **개인 판단과 설명문의 목소리 차이**
   - `_posts/2025-05-25-cloud_security.md:108`의 ‘신경써야 한다고 생각한다’와
     `:114`의 ‘제시합니다’가 이어진다. 어미를 맞추더라도 ‘생각한다’는 남겨야 한다.
   - `_posts/2018-05-27-problem_solve.md:144`는 자신의 문제 해결 방식에 대한 기록이고,
     `:150`부터는 설명형 문체다. 카테고리만으로 글의 문장 기능을 판단하기 어렵다.

3. **대화·강의형 설명**
   - `_posts/2023-05-15-kubernetes_engineering.md:477`의 ‘교과서적인 정의죠’와
     `:500`의 ‘머릿속에 새기세요’는 단순 어미 외에도 독자에게 말하는 방식이 강하다.
   - 수사적 질문, 비유, 강조를 모두 없애면 설명 정보와 저자의 목소리가 줄어들 수 있다.
     1차 교정에서는 이를 유지하고 종결 형식을 우선 맞춘다.

4. **1인칭과 독자 호칭**
   - `_posts/2018-01-01-mission.md:63`은 ‘저는’과 ‘나의’가 한 문단에 섞인다.
   - 한다체에서 자기 지칭은 문맥에 따라 ‘나/내/나는’으로 정리하되, 기존 생략 주어를
     매 문장에 추가하거나 저자의 판단을 일반적 사실로 바꾸지 않는다.

5. **정상적인 예외**
   - `_posts/2026-06-15-graceful_departure_checklist.md:207`의 작별 이메일은
     실제 사용을 위한 정중한 예문이다. 본문의 한다체와 별도로 원문을 보존한다.
   - ‘서버 구성’, ‘기밀 유지’, ‘~하기’ 같은 제목·체크리스트는 기능에 맞는 명사형을 유지한다.
   - `>` 표시는 외부 직접 인용이라는 보장이 없으므로 출처와 문장 기능을 확인한다.

## 교정 규칙

### 1차 교정 범위

- 한국어 서술문의 ‘~합니다/~입니다/~됩니다’를 ‘~한다/~이다/~된다’로 맞춘다.
- ‘~할 수 있습니다’는 ‘~할 수 있다’, ‘~생각합니다’는 ‘~생각한다’로 맞춘다.
- 문맥이 명확한 존대 자기 지칭을 정리하고, 교정에 직접 필요한 조사·띄어쓰기만 손본다.
- 질문은 ‘~인가?/~일까?’ 등 질문 기능을 유지한다. 답을 새로 써 넣지 않는다.
- 절차 안내와 자기 다짐은 지시·권고·선택·다짐의 기능을 유지한다. ‘~하자’를 단순한
  사실이나 실행 완료 문장으로 바꾸지 않는다.
- 대상에 대한 존칭과 주체 높임은 유지한다. 예를 들어 ‘하셨습니다’의 문장 끝을 바꾸더라도
  ‘하셨다’로 유지해 원문의 높임 관계를 보존한다.

### 원문 보존 조건

- 영문 본문, 코드 펜스, 코드·주석·실행 결과, 인라인 코드, 수식은 변경하지 않는다.
- 인용·대화·이메일·프롬프트 예시를 산문 교정과 분리한다.
- front matter, 파일명, 게시일, 공개 여부, 카테고리, URL, 이미지 경로는 그대로 둔다.
- 제목·제목 레벨·기존 앵커·섹션 순서·한영 구분선·목록 계층을 보존한다.
- 수치, 기간, 버전, 조건, 부정, 예외, 가능성, 시제와 행위 주체를 보존한다.
- 영문 기술 용어의 번역·통일, 사실 갱신, 설명 보강·요약, 비유 삭제는 이번 교정과 분리한다.
- 의심스러운 기술적·법적 주장은 별도 확인 목록에만 남기고 톤 교정 중 고치지 않는다.

### 의미 보존의 예

다음은 방향을 설명하는 예시이며, 실제 본문에 적용한 변경이 아니다.

| 원문 | 허용되는 교정 | 보존할 의미 |
| --- | --- | --- |
| 루씬을 이해하는 것이 성능 최적화에 도움이 됩니다. | 루씬을 이해하는 것이 성능 최적화에 도움이 된다. | 같은 설명·관계 |
| 클라우드 보안은 더 이상 단일 주체의 책임이 아닙니다. | 클라우드 보안은 더 이상 단일 주체의 책임이 아니다. | 부정의 범위 |
| 성능 최적화에 도움이 된다고 생각합니다. | 성능 최적화에 도움이 된다고 생각한다. | 저자의 판단이라는 성격 |
| Pod를 직접 생성하는 일은 거의 없습니다. | Pod를 직접 생성하는 일은 거의 없다. | ‘거의’라는 예외 가능성 |
| 계정이 탈취될 수도 있습니다. | 계정이 탈취될 수도 있다. | 확정이 아닌 가능성 |

‘탈취될 수도 있다’를 ‘탈취된다’로 바꾸거나, ‘권장한다’를 ‘반드시 해야 한다’로 바꾸는
편집은 허용하지 않는다. 날짜·경력·계획을 현재 시점에 맞춰 갱신하지 않는다.

## 권장 적용 순서

1. **원본 기준 확보**
   - 각 배치 시작 시 현재 원문을 다시 읽고 기준 해시를 기록한다.
   - 수정 중인 글은 현재 작업 내용을 기준으로 보존한다. 분석 당시 해시와 다르면 재분석한다.
   - 비발행 글의 공개 상태와 미추적 파일의 추적 상태를 의도 없이 바꾸지 않는다.

2. **대표 5편으로 규칙 검증**
   - Elasticsearch Concept: 혼합 어미, 정의, 목록.
   - Cloud Security: 개인 판단과 안내문 혼재.
   - Kubernetes Engineering: 긴 기술 글, 대화체, 코드·표.
   - Who am I?: 자기소개, 1인칭, 신앙·가치관과 존칭.
   - Graceful Departure Checklist: 지시형과 작별 이메일 예외.
   - 파일 전체 재생성 대신 바뀌어야 하는 문장에 한정해 변경안을 만든다.

3. **10~15편씩 확대**
   - 같은 글 안에서 어미가 혼용된 19편 후보를 먼저 본다.
   - 합니다체 우세 글, 메모·목록 위주 글, 개인 기록을 나누어 적용한다.
   - 이미 한다체인 부분은 유지하고 불필요한 문장 재작성은 줄인다.

4. **배치별 검증과 검토**
   - 보호 구간의 원문 일치, Markdown 구조와 링크·제목·수치·코드의 보존을 자동 검사한다.
   - 바뀐 문장의 전후를 읽어 부정·조건·가능성·시제·주체·권고 강도를 검토한다.
   - 큰 구조 변경이나 예상보다 많은 삭제는 검토 대상으로 멈추고 원인을 확인한다.
   - Jekyll 빌드와 내부 링크 검사를 실행한다. 대표 글의 EN/KR 전환과 목차도 확인한다.
   - 자동 검사와 별도 문장 검토를 함께 사용한다. 빌드 성공과 문장 유사도 점수만으로
     의미 보존이 증명되지는 않는다.

5. **재발 방지**
   - 확정된 규칙을 글쓰기 지침과 새 글 생성 프롬프트에 반영한다.
   - 새로 추가된 존댓말 후보를 검출하되, 인용과 예문 예외를 검토할 수 있게 한다.

초기 분석 단계에서는 분석 문서와 글별 목록만 추가했다. 이후 수행한 본문 교정과
검증은 [교정 결과](editorial-tone-results.md) 및 GitHub 배포 기록에서 확인할 수 있다.
